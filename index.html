01 — About

What keeps me curious

I don't usually start with a project idea.
I start with a question.

Sometimes it's about why a model trusts something it shouldn't. Sometimes it's about why people click "Accept" without really knowing what they're agreeing to. Sometimes it's simply trying to understand what happens when one small assumption in a system changes.

Most of the things I've built started that way.

I studied cybersecurity because I wanted to understand how systems break. Somewhere along the way, that curiosity pulled me toward AI, privacy, and the less obvious parts of security.

I like building things, from security tools to a vocabulary app I made for my own GRE prep, but I'm probably just as interested in taking them apart, testing the assumptions, and figuring out where the interesting problems actually are.

I'm still learning. A lot.
And I'm usually happiest when there's something I don't quite understand yet.

The question

Could I build the GRE vocabulary tool I couldn't find, with no account, no ads and no network, and still build it like something you'd trust?

The approach

I was preparing for the GRE, couldn't find good resources, and found learning that many words hard, so I built the tool I wanted. I treated it as a privacy rule: the safest data is data you never collect. Everything stays on the phone. The parts that read outside data, backup codes and saved storage, are handled as untrusted input. The web code is plain JavaScript with no runtime dependencies, wrapped for Android with Capacitor.

Android only, and independent of ETS. Saved progress is not encrypted, and the Android backup setting is a manual step with no test. Both are listed in the threat model. Word selection was informed by community GRE lists; the meanings, sentences and memory tips are my own writing.
GitHub ↗
What I built
  • 550 words across 55 levels, fully offline
  • Learn, swipe, fill-in and quote modes with spaced review
  • 8 themes checked for contrast
  • 48 px touch targets, screen-reader-friendly wheel
  • Backup codes with undo
  • Recovery screen instead of a blank page
Technical decision

Progress is saved by fixed ids with a format version, not by list position, so adding or moving content never shifts anyone's saves. Old saves upgrade once and a copy is kept. A test fails if an id ever changes.

How I tested it

38 app tests, 30 security tests and data checks on all 550 words, run in CI with npm audit. The backup reader is tested with a decompression bomb, prototype-pollution keys, tampered checksums and stored-XSS text. A browser test proves the Content Security Policy blocks inline scripts, eval and network calls.

The question

Can you detect a hidden backdoor in a model without having the poisoned training data?

The approach

RBD++ uses reverse distillation to audit a suspicious model with only query access and a small trusted dataset. It probes the model around a suspected trigger region, distills that behavior into a student model, then compares it against clean and poisoned shadow populations.

Research prototype, not a production security product. There are still open questions around adaptive attackers, false positives, framework coverage, and real deployment environments. I'm currently writing this up as a proper paper and will update this section once it's done.
GitHub ↗
What I built
  • Poison-and-detect pipeline, on a real backdoored model
  • Control-run mode, tested against a clean model
  • Poison-rate sweep with bootstrapped confidence intervals
  • Mixed shadow ensembles (MLP, SVM, decision tree)
  • Image-model backdoor detection
  • Hidden trigger-word detection in language models
  • Federated-learning update screening
  • RAG pipeline poisoning detection
  • CLI dashboard for pipeline stage tracking
What I learned

The most useful part of this project wasn't getting the detector to work. It was finding out where it didn't. Clean-only distillation initially missed a model with a measured 100% attack success rate. Raw-logit distillation was dominated by extreme outliers. Fixing those problems changed the project more than the original implementation did.

The question

What exactly am I agreeing to when I click "Accept"?

The approach

ConsentLens started from a fairly ordinary annoyance: privacy decisions often happen through tiny buttons and very large policies. The idea was to make some of that information easier to understand before consent is given. It scans locally first, labels uncertainty clearly, and only contacts a backend when you ask for deeper analysis.

An MVP. Consent managers change their markup often, policy parsing is guidance and not legal advice, and the service database is still small. An unknown domain shows as "Unclassified third party", never as safe or unsafe, and nothing is labelled "verified".
GitHub ↗
What I built
  • Per-site risk score, with reasons and stated uncertainty
  • Tracker mapping and fingerprinting hints
  • OAuth scope heatmap (Low to Critical)
  • Warning before positive consent clicks
  • Local consent receipts and timeline
  • Data-rights request drafts
  • Source-backed profiles with a reviewer queue
How I tested it

Fixture tests for consent-manager flows (OneTrust, Didomi, Sourcepoint), storage validation and risk wording, plus backend tests that include SSRF checks against private addresses.

What I learned

Privacy isn't only a policy problem. It's also an interface problem. If the information people need is technically available but practically unreadable, the system is still asking them to trust something they can't easily understand.

The question

What does a network actually look like once you stop thinking about hosts as isolated machines?

The approach

NetMap combines network discovery with security intelligence to turn scan results into something closer to an attack-surface map.

A research and education tool, not a replacement for Nessus or OpenVAS. CVE matching is keyword-based rather than exact, and the ATT&CK mapping is a small hand-curated table. Only scan networks you own or are authorized to scan.
GitHub ↗
What I built
  • Host and service discovery
  • Network topology mapping
  • CVE matching (keyword-based)
  • EPSS-based prioritization
  • MITRE ATT&CK mapping
  • Optional OSINT (Shodan, WHOIS)
  • Historical change tracking
  • Rogue-device detection
  • Interactive topology visualization
  • HTML security reporting
How I tested it

A pytest suite runs in CI on every push, with the network mocked. A self-review found a stored-XSS bug in the HTML report. It's fixed, and the tests now cover escaping. An evaluation harness against Metasploitable2 is included.

What I learned

A list of vulnerabilities tells you what might be wrong. A map starts showing you where it matters.

04 — Writing

I write when something won't leave my head alone.

Usually it's a question about security, AI, or the strange places where technology starts behaving differently from what we expect. Writing also forces me to figure out what I actually think.

One I'd start with

A 99% Accurate AI Model Can Still Fail You

Accuracy is the number everyone compares: benchmark scores, leaderboards, one model beating another by a few points. This piece argues accuracy only answers one question, how often the model was right during testing. It doesn't say whether the model can be manipulated, whether it leaks sensitive information, or whether a hidden trigger is sitting quietly inside it. It walks through real cases (a data-leak incident, a biased hiring model, prompt injection, backdoors, model extraction) where the accuracy number stayed fine while everything else quietly went wrong.

Accuracy measures performance. It doesn't measure trust.
